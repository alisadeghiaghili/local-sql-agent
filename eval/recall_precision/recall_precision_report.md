# Recall / Precision Evaluation — NLQ Interpretation Pipeline

_Benchmark over the IME auction warehouse NLQ system. Generated by `make_report.py` from the most recent run — re-run it after any re-execution to refresh every number below._

## 1. Scope and method

The benchmark measures how faithfully the system **interprets** a Persian
business question — i.e. which requirement items it extracts — rather than
whether the final SQL string matches a reference. Two layers are scored:

| Layer | What it is | Needs model? | Role |
|---|---|---|---|
| **B** | Full production pipeline: real model (Qwen3.8-27B-FP8) + live warehouse; the generated T-SQL is parsed back into a requirement set. | yes | **Headline** — end-to-end interpretation |
| **A** | Deterministic pre-LLM retrieval only: the ring filter and Persian-calendar date facets that `ValueRetriever`/dimension matching resolve before any model call. | no | Diagnostic of the value-extraction component |

A **requirement** is one typed fact the question demands: `metric`, `entity`,
`filter`, `date`, `grouping`, `ordering`, `top`, or `exclusion`. Scoring is
semantic, not string-equality: ring names match by stored value, relative
dates and exclusions match by *column*, ordering by sort direction, grouping by
grouped column, and `COUNT(id)` is treated as equivalent to `COUNT(*)`.

- **Recall** = (required items correctly extracted) / (required items).  A missing
  requirement is *not* counted against precision.
- **Precision** = (correctly extracted) / (all extracted).  An unsupported extra
  is *not* counted against recall.
- **Macro** = mean of per-case values.  **Micro** = pooled items across all cases.

Layer A intentionally scores only ring + date facets: choosing the metric column
(business-rule driven) and entity/table selection are the model's job and are
scored in Layer B. So a low Layer-A recall on a `multi`/`aggregation` question
means *the deterministic layer does not resolve that filter type*, not that the
final answer is wrong.

## 7. Dominant error: cross-warehouse mis-routing

Of 100 cases, **14 mis-route to the futures/CSD warehouse** instead of
the auction warehouse — `Future_Fact.Trade` (with `Future_Dim.Contract`) or the CSD
`vTrades` views. Distribution by category:

- **ambiguous**: 8
- **analytical**: 3
- **simple**: 1
- **date**: 1
- **aggregation**: 1

Trigger is generic, unanchored phrasing — `معامله` (trade), `قیمت` (price), `حجم`
(volume), `آمار` (statistics) — which the model maps to the futures `Trade` fact. The
auction facts are only chosen when the question is *anchored* to an auction word

## 8. Common interpretation errors (summary)

1. **Cross-warehouse mis-route** (14 cases) — the biggest issue; generic trade/price/
   volume words resolve to `Future_Fact.Trade` rather than the auction facts.
2. **Symbol grouping lost** — top-symbol questions miss the `Symbol` entity and the
   `GROUP BY symbol` (4 misses each); the model groups by contract/customer instead.
3. **Offer-kind / clearing-kind / currency / contract-kind filters dropped** — the
   multi-condition filters the deterministic layer can't resolve and the model often
   omits or guesses (e.g. `OfferKind=export`, `Currency=دلار`, `ClearingKind=نقدی`).
4. **Ring sometimes dropped on a single filter** — 5 cases lost the ring filter,
   usually when the mis-route also replaced it with a futures commodity-group filter.
5. **`COUNT` vs row-list** — a few questions asking for a count got a row listing
   (or vice-versa); the metric type was off even when the table was right.
6. **Day-of-week** — `PersianDayOfWeek` extraction is fragile (شنبه=1 was read as 6 in
   one case), so weekday-anchored questions under-performed.
7. **Strong spots** — exact Persian dates, seasons, top-N by value, and exclusion
   filters (not-cancelled, not-premium) were handled well; negatives averaged 96.7% recall.

## 9. Recommendations

**For the NLQ pipeline (highest impact first):**

1. **Fix cross-warehouse routing.** This deployment's default source is `Auction_DM`,
   yet unanchored questions flip to `Future_DM`. Options: (a) bias the source selector
   toward the default/auction source when the question names no futures-specific term;
   (b) teach the retrieval layer that `معامله`/`قیمت`/`حجم` are auction-ambiguous and
   should default to the auction facts or trigger a clarification rather than silently
   choosing futures; (c) add the auction facts' Persian aliases (معامله→Contract/Trade)
   so the auction source wins the keyword tie. This alone would recover ~14 cases.
2. **Strengthen symbol handling.** `Symbol` grouping is repeatedly dropped on top-N
   commodity questions; ensure the `Symbol` dimension is retrieved and the GROUP BY is
   preserved when a question references `نماد`/commodity.
3. **Surface the unresolvable filters as clarifications.** Customer type, currency,
   offer/clearing kind are not in the deterministic tier and are frequently dropped.
   Declaring them as assumptions/clarifications (as the ranking flow already does) would
   convert silent misses into visible, correctable choices.
4. **Robust weekday extraction.** Persian-day-of-week mapping has off-by-one cases; the
   `extract_day_of_week` patterns should be re-validated against the 1380–1408 date table.

**For this benchmark:**

- The futures mis-route is a *source-selection* defect, partially outside pure
  interpretation; it is counted here because a wrong-domain answer is an incorrect
  interpretation. A future revision could report it as a separate axis so the two
  failure modes (right warehouse, wrong filter vs. wrong warehouse) stay distinguishable.
- Layer A is a stable, model-free regression signal: it can be run in CI without the
  LLM or warehouse to catch retrieval/alias regressions cheaply.
